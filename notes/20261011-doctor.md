Status: complete, 2026-10-12; both phases landed.

## What exists that this builds on

- `fm doctor` is the workshop's, in `livery.workshop._ci_tasks`: it
  prints who you are on the forge, the server version, the capabilities
  granted and missing, unknown declared owners, the admin token ladder,
  the host compilers the present kinds need and the tools served from
  the host. It fixes nothing, and no other package can add a line.
- `fm janitor` is footman's, in `livery.footman._tasks.janitor`: footman
  collects its own cache, then runs every sweeper an installed package
  registers under the `footman.sweepers` entry-point group. A sweeper is
  a callable taking `data_dir`, `cache_dir`, `config_dir`, `dry_run` and
  `now` and returning the lines it wants printed; one that raises is
  named and the rest still run, one whose entry point cannot load is
  named and skipped. The workshop registers one.
- The tool store's probe, `Store.probe` in `livery.toolroom.store`,
  answers whether a locked tool is present: the ref matches the
  catalogue's record, a view record exists for the tool directory, and
  every file the record names exists on disk. The sync runs it for every
  locked tool; the file walk is 0.4 to 0.5 s of a quiet sync's local
  second, nine views, node alone thousands of files. It guards against a
  view damaged after it was made, which nothing in the gate causes.
- `fm check --fix` is the vocabulary for a verb that judges by default
  and rewrites on the flag.
- Layering: `livery-toolroom-store` depends on strongroom and toolroom
  and never on footman. toolroom already works with footman without
  depending on it: `livery.toolroom.tools` routes every call through
  footman's `run()` when footman is live in the process, found in
  `sys.modules`, and never imports it. An entry point under
  `footman.doctors` is metadata in `pyproject.toml`, loaded only by
  `fm doctor`, so the store registers its doctor the same way.

## Ground-truth contracts (do not violate)

1. **footman owns the verb.** `fm doctor` is footman's, like `fm
   janitor`: footman's own checks first, then every doctor an installed
   package registers under `footman.doctors`. No check lives in the verb
   itself beyond footman's own.
2. **A doctor reports findings, never prose.** A finding names what was
   checked, what was found, and the fix: an action the doctor can run,
   or words when only a person can act. The lines `fm doctor` prints are
   rendered from findings, so every finding reads alike.
3. **The plain verb judges; `--fix` repairs.** `fm doctor` runs no
   action. `fm doctor --fix` runs every finding's action, checks again,
   and reports what is healthy and what still stands with its reason.
   Idempotent: a second `--fix` finds nothing to do.
4. **A doctor's failure is its own.** One that raises is named and the
   others run; one whose entry point cannot load is named and skipped;
   a fix that fails leaves its finding standing with the reason. The
   verb's exit code is red when a finding stands after the run.
5. **A doctor needs no dependency on footman.** A finding is a plain
   shape footman documents, four attributes, and footman reads it by
   its attributes; a package that never imports footman returns its
   own. The store's doctor lives in the store, beside the views it
   judges.
6. **A sync still supplies what is missing.** The probe keeps the ref
   check and the record check: a tool the lock moved, or a view never
   made, is supplied at sync as today. Only the file walk leaves the
   sync.
7. **A doctor says what it reaches.** footman's own checks read the
   machine alone; a registered doctor that reaches a forge says so in
   its finding. What is wrong with CI, the forge, its grants, its
   owners, is a doctor's to report: that is the place for it.
8. **The nightly starts with `fm doctor`.** Its findings are the first
   lines of the night's record; a standing finding is red there as
   anywhere.

## The design

### The finding

One shape, documented by footman and read by its attributes, so a
package returns footman's `Finding` when it imports footman and its own
four-attribute object when it does not:

- `what`: the check and its answer, short, the way a receipt names a
  step; a healthy check prints this line alone.
- `found`: what is wrong, one sentence; empty for a healthy check.
- `fix`: the words a person acts on, always present on a standing
  finding.
- `repair`: an action the doctor can run, or none.

A doctor is a callable registered under `footman.doctors`, taking the
same keyword arguments a sweeper takes less `dry_run`, plus `fix`, and
returning its findings. Under `fix` it runs each finding's repair, then
checks again and returns what stands.

### footman's own checks

The runner's directories exist and are writable; the `fm` on PATH is
this environment's or hands off to it; the cache collector's stamp is
not from a dead process; the scratch directory holds nothing of a gone
process. Each with a repair where one is safe: making a directory,
sweeping a dead process's scratch.

### The workshop's doctors

Two registrations, both moved from the verb the workshop has today, with
their words unchanged:

- the forge doctor: identity, server, grants, owners, the admin token
  ladder. It reaches the forge and says so. No repair: every fix is a
  person's.
- the host doctor: the compilers the present kinds need, the tools the
  host serves. No repair.

### The store's doctor

`livery.toolroom.store` registers one doctor, in a module of its own
that imports nothing of footman and reads nothing outside the store:

- every view the store made under its home, from its own view records,
  with the files each record names that the disk lacks; the finding
  names the tool, the version and the missing paths, and its repair
  drops the view's record and views the same tree again at the same
  directory. The tree's blobs are in the object store already, so the
  mend fetches nothing and reads no lock and no catalogue.
- the public calls behind it, `Store.audit(name, version)`,
  `Store.audit_views()` and `Store.mend_view(name, version)`, so the
  workshop or a person can do the same from code.

The sync's probe stops walking: `Store.probe` keeps the ref and the
record checks.

### What it does not cover

A view damaged between syncs is found by `fm doctor` or by the tool
failing, and repaired by `fm doctor --fix`; the sync does not heal it.
A check leg does not run `fm doctor`; its views are made fresh per job.
The nightly does, first.

## Phases

### Phase 1: footman's `fm doctor` and the workshop's checks behind it

Deliverables:

- `livery.footman._tasks.doctor`: the verb, `--fix`, the `Finding`
  shape and the `footman.doctors` group, public names documented on the
  API page and in `configuration.md` beside the sweepers.
- footman's own checks, with their repairs.
- the workshop's forge and host doctors registered in its
  `pyproject.toml`; `livery.workshop._ci_tasks.doctor` goes.
- the nightly point runs `doctor` as its first scheduled entry, before
  `check`, in the builtin schedule `fm ci.run` executes; a standing
  finding fails the night. No line of YAML changes.
- tests, fallbacks first: a doctor that raises is named and the others
  run; one that cannot load is named and skipped; a repair that fails
  leaves the finding with its reason; `--fix` twice finds nothing the
  second time; a standing finding exits red.

Acceptance:

- `fm doctor` in this checkout prints the forge and host lines it
  prints today, under footman's own, and exits 0.
- `fm doctor --fix` exits 0 and prints nothing repaired on a healthy
  machine.
- `fm --all --help` lists `doctor` under footman, not the workshop.
- `entries_for(root, "nightly", "nightly")` opens with `doctor`, pinned
  by the points test; `fm ci.e2e --scenario=release` green with it.
- `fm check` green.

### Phase 2: the view walk leaves the sync

Deliverables:

- `Store.audit`, `Store.audit_views` and `Store.mend_view`, public,
  tested in the store.
- the store's doctor, registered in `packages/toolroom-store/
  pyproject.toml`, importing nothing of footman; its finding and repair
  tested by deleting a file under a supplied tool's view: `fm doctor`
  names the tool and the path, `fm doctor --fix` views it again from
  the store with the origin unreachable, a second `--fix` finds nothing.
- `Store.probe` without the file walk; a test pins that a probe of a
  present tool stats no entry of its view.

Acceptance:

- `fm --profile=<file>.json sync` on a current checkout: the `sync
  tools` step under 0.1 s, read off the trace.
- a file deleted under `tools/node/<version>/`: `fm doctor` exits red
  naming it, `fm doctor --fix` exits 0 and the file is back, `fm
  doctor` exits 0.
- `fm check` green.

- 2026-10-11, Willem: the view walk leaves the sync; `fm doctor` owns
  it. footman owns the verb with a hook for plugins and extensions, the
  janitor's shape. A doctor fixes what it can, under `--fix`, the gate's
  vocabulary.
- 2026-10-11, Willem: the store's doctor lives in toolroom, not the
  workshop; toolroom already works with footman without depending on
  it, and a finding needs no import of footman. The nightly runs `fm
  doctor` first. What is wrong with CI is a doctor's to report, so the
  forge checks stay under it.

- 2026-10-11, phase 1: a healthy check prints its line on the plain
  verb, not only under `--verbose`: `fm doctor` is a report a person
  reads, and the acceptance wanted today's lines. The nightly's doctor
  is a schedule entry, not a rendered step: the entries are what `fm
  ci.run` executes, so no YAML moves. An extension a wheel ships that
  the workspace does not list is information, not a finding that
  stands: the common case for a python-only workspace.

- 2026-10-12, phase 2, Willem: the doctor reimplements nothing. The
  first draft resolved the lock and the catalogue the way the workshop
  does, to supply a damaged tool again; the store already holds the
  tree a view presents, so the repair views that tree again and needs
  neither. `Store.resupply(record, version)` from the plan became
  `Store.mend_view(name, version)`, and the doctor reads only
  `data_dir`. The three copies the draft exposed moved down into the
  store for every caller: `Catalogue.at` and `is_records` decide
  records against an index once, `index_source` reads the
  `[toolroom] index` key, `Home.under` places the home; the workshop's
  `_tools.py` calls them and lost its own.

- 2026-10-12, Willem: a pull request's check legs run on every runner.
  Phase 2 could not clear toolroom-store's 100% floor on the ubuntu leg
  alone: the Windows-only branches are unreachable there, and the rows
  carried from main's records sit at main's line numbers once a change
  moves the file (#1499). The contract's `pull-request-runners` names
  the three runners; the merge point and the nightly already did.
